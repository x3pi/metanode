Fault injection: val0's NOMT dir on a 268 MB tmpfs (265 MB used at start), 4 validators, `secp_tps_blast -count 400000` (50000 txs were actually sent).
run3 = binary before the fix (bins_dev2): val0 keeps running after ENOSPC, block hash differs from block 4 on.
run4 = binary with fail-stop in CommitAsync (bins_fix): val0 exits at the first failed commit, val1..3 agree.
Reproduce: `sudo mount -t tmpfs -o size=268m,uid=$(id -u) tmpfs /mnt/nomt_small; python3 enospc_inject.py <bins> /mnt/nomt_small <outdir>`.
run5 (`enospc_recover.py`, binary with fail-stop): after val0 exited on ENOSPC, the tmpfs was remounted to 700 MB and `run_env.sh start_node val0` restarted it. 40 s later all four validators were at height 6 with identical block hash and stateRoot (`recover_summary.json`). Cluster was idle after the load; recovery under continuing load was not tested.
run6 was INVALID (val0 failed to bind port 31646 because a duplicate val0 started by an earlier script version was still running) and is not kept.
run7 and run8 (`enospc_ns.py <bins> account_state <out> 3`, binary rebuilt after the unit-test seam, guards against leftover processes and double starts): account_state dir on a 17 MB tmpfs.
- Phase 1 (50000 txs): val0 exits at the first failed commit, val1..3 keep going.
- tmpfs remounted to 900 MB, val0 restarted.
- run8: val0 caught up in 34 s (height 6), phase 2 (50000 new txs, all 4 up): loss 0, parity OK at #10, hash/stateRoot identical on all four, 100000 txs in the chain on val0 and val1 (`run8_val*_commits.txt`).
- run7: phase 2 was started while val0 was still catching up (height 2 of 7). Parity was still OK (#15, identical on all four) but 8301 of the 50000 phase-2 txs were never committed (loss_vs_sent 8301, `run7_p2.out`: validators report received=50000 rejected=0). Cause (investigated 2026-10-20): the blast tool fetches each account's starting nonce with `eth_getTransactionCount(pending)` from a node (`cmd/tool/secp_tps_blast/main.go:320,621`); the accounts served by the lagging val0 got stale nonces, so their txs were rejected as nonce too low. The logs show it explicitly: `code=26 ... tx.GetNonce() < as.Nonce(): 1 < 2` at admission (125 of 500 in several batches on every node) and `FAST-PATH-NONCE-REJECT total 2864 txs` in blocks, whereas run8 (val0 caught up first) has 0 of both. So the loss is a client-side stale-nonce artifact, not silent loss on the node; the exact 8301 was not reconciled against these counters (admission errors and block-level rejects may overlap). `received=50000 rejected=0` in the tool counts raw receipt only.
`stake_db` and `smart_contract_storage` were not driven: `secp_tps_blast` sends plain transfers only, which never write them (the stake_db tmpfs stayed at 251 MB used); the code path is the same `CommitAsync`.

run9 (`enospc_ns2.py <bins> smart_contract_storage <out> 1`, tool `cmd/tool/nomt_ns_blast`): the contract-storage namespace on a 2 MB tmpfs, 10000 SSTORE txs. val0 exited with `NOMT async persistence failed (namespace=smart_contract_storage_<contract addr>, block=6)` after `No space left on device (os error 28)`; val1..3 continued; tmpfs grown, val0 restarted, a second contract deployed and called: all four at height 10 with identical hash/stateRoot (`run9_sc_*`). Note the namespace is per contract.
`stake_db` cannot be driven to ENOSPC this way: its hash table is preallocated (64000 pages = 251 MB, fully allocated), so delegate txs (status 1, verified via receipts) overwrite in place and the tmpfs usage stayed at 251 MB with 3 MB of headroom. A disk-full failure there would need metadata/WAL growth or a fuller table; `[CHƯA ĐO]`.

run10 (`eio_inject.py <bins> stake_db <out>`, needs root for loop/dm/mount): `stake_db` on an ext4 filesystem over a device-mapper device (512 MB). After startup the table is reloaded as `flakey ... error_writes`, so every write to the device fails with EIO while reads still work. 4000 `delegate` txs follow. val0 exited with `nomt_commit_payload failed: Input/output error (os error 5)` then `NOMT async persistence failed (namespace=stake_db, block=2)`; val1..3 reached height 3. The device was restored to `linear`, the fs checked (`e2fsck -fy`) and remounted, val0 restarted, caught up, a second batch of 4000 delegate txs was sent and all four validators were at height 5 with identical hash and stateRoot (`run10_*`). The original incident (ledger #15, `stake_db`, block 45) therefore has a reproducible I/O-failure route and the same signature (`failed to commit payload` followed by `Store is poisoned`); whether the original cause was EIO, ENOSPC or something else is still unknown.
